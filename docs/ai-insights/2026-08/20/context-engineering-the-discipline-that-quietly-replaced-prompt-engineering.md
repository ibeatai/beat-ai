# 上下文工程：悄然取代 prompt 工程的学科

prompt 工程旨在找到合适的词语。上下文工程则旨在决定模型究竟能看到什么——这是 Agentic AI 中最关键的技能。这是一份深入全面的指南。

![图 1：prompt 工程优化了一条消息。上下文工程则策划模型的整个世界。](https://cdn.jsdelivr.net/gh/genesislab-io/beatai-assets@5ab0231c168bc3d9d525e2de753e3f39fad885a4/ai-insights/2026-08/20/images/context-engineering-the-discipline-that-quietly-replaced-prompt-engineering/01.webp)

这次失败让我学到的东西比任何成功都多。我观察的一个 agent 一开始执行重构任务时，手法精准如手术刀：计划清晰，修改合理，每次修改后都进行测试。然而，90 分钟后，它却判若两人。它重新读取了已经读取过的文件，提出了一个已经尝试过的修复方案，最终——这才是最令人痛心的地方——竟然公然违反了任务开始时设定的唯一约束。模型本身并没有改变，改变的是上下文：90 分钟内累积的工具输出、错误转储和半相关的文件内容，将最初的目标淹没在了 15 万 token 的沉积物之下。

这个模型不是变笨了，而是*快要淹死了*。

这就是为什么这个领域最顶尖的专家们在某个阶段不再使用“prompt 工程”这个词，而是开始使用**上下文工程**。prompt——那些你编写的巧妙指令——最终只占塑造 agent 行为因素的十分之一。其余的因素则是模型在每个步骤中关注的其他所有内容：消息历史记录、工具定义、工具结果、检索到的文档、记忆文件、错误跟踪等等。决定哪些信息可以保留、哪些信息需要移除，以及哪些信息应该被移除，如今已成为构建 agent 的核心技巧，使其在十分钟后依然保持智能。

这是我关于 Agentic AI 系列文章的第三篇——第一篇介绍了 harness，第二篇介绍了追踪和可观测性。本文将深入探讨贯穿这两篇文章的核心原则：如何在任务长时间运行时管理模型的工作记忆。一如既往，本文从基本原理出发，逐步过渡到生产模式，并辅以案例研究。无需任何先验知识，也绝非浅尝辄止。

## 第一部分：上下文的真正含义（以及它为何会退化）

## 上下文窗口的结构

人们说“prompt”时，通常会想到自己输入的文本信息。但实际上，模型每次调用接收到的都是整个组合：

**系统 prompt**（身份、规则、行为）、**工具定义**（agent 可以调用的所有工具的 schema——通常本身就有数千 token）、启动时加载的**记忆文件**、**消息历史记录**（到目前为止的每一步），以及该历史记录中真正占用空间的部分：**工具结果**——文件内容、搜索结果、API 响应、堆栈跟踪、屏幕截图。

对于成熟的 agent 来说，你手写的指令几乎可以忽略不计。我分析过一些 agent 上下文，其中系统 prompt 只占窗口的 3%，而工具结果却占了 70%。如果你只关注那 3% 的部分，就好比是在调整引擎盖上的贴纸，却忽略了引擎本身。

## 关于长上下文窗口的令人不安的真相

现代上下文窗口的容量从 20 万到 100 万 token 不等，而市场宣传却暗示你可以直接使用它们。但事实并非如此，这并非易事，原因有二，而这两个原因在规格表中并未提及。

首先，**注意力在整个上下文窗口中并不均匀分布。**模型对上下文的开头和结尾的关注度最高；中间的信息则更容易被遗忘。研究人员称之为“中间迷失”，而每个实践者都曾独立地重新发现过这一点，通常是在凌晨两点。你从第三条消息中得到的关键限制，实际上就像是在体育场最后一排低声耳语。

其次，**性能会随着窗口内容的填充而下降——甚至在达到上限之前。**这就是人们所说的“上下文腐化”：大海捞针式的基准测试结果依然亮眼（它们测试的是对预设信息的检索），但对填充窗口进行实际推理时，性能会明显下降。模型开始对它看到的绝大多数信息进行模式匹配，而不是针对真正重要的信息。填充窗口很容易，但如何在填充过程中保持模型的*敏锐*才是关键所在。

![图 2：窗口逐渐被填满；但有效注意力却无法随之扩展。目标在达到极限之前很久就已模糊不清。](https://cdn.jsdelivr.net/gh/genesislab-io/beatai-assets@5ab0231c168bc3d9d525e2de753e3f39fad885a4/ai-insights/2026-08/20/images/context-engineering-the-discipline-that-quietly-replaced-prompt-engineering/02.webp)

## 上下文出错的四种方式

从业者们一致认可的分类法，值得牢记，因为你会遇到所有四种情况：

**上下文污染**——错误或幻觉进入上下文，并在后续步骤中被*当作真理*处理。例如，步骤 12 中一个虚构的文件名成为了步骤 13 到 40 的基础。

**上下文干扰**——海量累积的内容淹没了指令。模型开始模仿自身的历史记录，而不是重新进行推理。（如上图所示，是我的重构 agent。）

**上下文混淆**——无关信息影响输出。任务只需要三个工具定义，却出现了四十个；模型调用了其中一个无关的工具定义，仅仅因为它*存在*。

**上下文冲突**——上下文的不同部分相互矛盾，模型没有原则性的选择方法。例如，旧需求与新需求、过时的文件内容与当前文件内容、两个不一致的搜索结果。

请注意，这四个问题都是内容管理失误，而非模型故障。这正是上下文工程乐观的核心所在：这些都是可以修复的错误，无需等待更好的模型。

## 第二部分：经济学——KV Cache 素养

在讨论技巧之前，先说说钱。几乎所有相关文章都会忽略这一点，而这正是 agent 每次运行成本从几美分到几美元之间的区别所在。

agent 的流量模式极其不平衡：它可能需要消耗 100 个输入 token 才能生成 1 个，因为每次循环迭代都会重新发送整个累积的上下文来生成一个很小的决策。服务提供商针对这种流量模式提供了**prompt 缓存**：如果上下文的开头（*前缀*）与之前的调用完全相同，则会重用其耗时的注意力计算，而不是重新计算。缓存的输入 token 成本约为新 token 的十分之一，处理速度也显著提升。

实际操作规则直接从机制中自然而然地得出：

**保持前缀稳定。**系统 prompt 和工具定义优先级最高，因此对它们的任何更改都会使后续所有内容的缓存失效。一个典型的自作自受的例子是：系统 prompt 顶部的时间戳。位置零处的单个 token 发生更改，就会导致每次调用都要重新支付整个上下文的全部费用。我见过这一项就让 agent 的账单翻了十倍。

**追加，不要编辑。**历史记录应该只允许追加。如果返回并修改之前的消息（例如重新格式化或“清理”），则会使该点之后的缓存失效。这也是为什么以下几种技术都被设计为*追加*操作的原因。

**请勿在会话期间添加或移除工具。** 工具定义位于前缀中。更换工具集会使缓存失效，并且当历史记录引用已不存在的工具时，会导致模型混乱。如果需要动态限制工具，请**屏蔽**它们（在决策时使其不可选择），而不是删除它们的定义。

![图 3：稳定的前缀意味着每个新回合只需支付新 token 的全价。顶部一个字节的更改会重新计算所有 token 的价格。](https://cdn.jsdelivr.net/gh/genesislab-io/beatai-assets@5ab0231c168bc3d9d525e2de753e3f39fad885a4/ai-insights/2026-08/20/images/context-engineering-the-discipline-that-quietly-replaced-prompt-engineering/03.webp)

将这些内化于心，许多“最佳实践”就不再是空谈，而是显而易见的后果：系统 prompt 当然是静态的；时间戳当然应该放在工具结果中，而不是放在前言中；压缩（如下）当然应该作为新的摘要而不是通过编辑历史记录来完成。

## 第三部分：工具箱——六种真正有效的技巧

生产环境中的上下文管理都是六种手段的某种组合。我将按复杂程度递增的顺序逐一介绍。

## 1. 严格筛选所有入选内容

最省事的办法就是永远不承认。具体来说：工具结果应该返回模型所需的*内容*，而不是 API 返回的内容——一个搜索工具如果只返回标题加摘要就能满足需求，却返回 20 个完整的文档，这是上下文错误，而不是工具本身的特性。设置合理的默认值（读取 200 行，而不是整个文件）。系统 prompt 要写得恰到好处——既要足够具体以提供指导，又不能过于详尽以至于成为模型必须不断重新解析的僵化规则。切忌“以防万一”预加载数据；这种想法正是上下文窗口走向衰亡的根源。

## 2. 压缩：刻意遗忘的艺术

主力模型。当窗口接近容量上限（生产系统会在 70-85% 左右触发）时，模型会被要求总结到目前为止的对话；总结结果会*替换*大部分历史记录；循环继续，并打开一个新的窗口，该窗口的开头是：系统 prompt、任务、总结、最近的对话轮次。

精髓完全在于*保留下来的内容*。一个好的压缩 prompt 会保留：已做出的决策及其原因、发现的限制（例如“API 拒绝超过 100 个元素的批次”）、精确的标识符（文件路径、函数名、ID——这些信息无法通过改写保留）、当前进度以及未解决的问题。它会果断地舍弃：原始工具输出（保留从中得出的结论）、死胡同探索（只保留一行：“尝试了 X，失败了，因为 Y”）以及无关紧要的客套话。

![动画：上下文窗口在 agent 运行过程中逐渐填满，达到阈值后进行压缩——摘要进入，沉积物排出，工作继续。](https://cdn.jsdelivr.net/gh/genesislab-io/beatai-assets@5ab0231c168bc3d9d525e2de753e3f39fad885a4/ai-insights/2026-08/20/images/context-engineering-the-discipline-that-quietly-replaced-prompt-engineering/04.gif)

压缩是有损的——这正是关键所在——但这种损失是*精心选择的*，而非随机的，这就好比是像档案管理员一样遗忘，还是像脑震荡一样遗忘。测试压缩 prompt 的方式应该和测试代码的方式一样：分别运行启用和禁用压缩的长时间任务，并比较结果。糟糕的摘要器会造成上下文污染，并增加额外的步骤。

## 3. 外部存储器：文件系统是最大的上下文窗口

这个领域最精妙的想法是：不要再把模型窗口当作唯一的记忆。给 agent 一个文件系统，并养成记录信息的习惯。计划写在 `plan.md` 里，发现的结果积累在 `notes.md` 里，中间结果则保存在实际文件中。agent 会在需要时重新读取这些文件。

这巧妙地反转了问题。不再是“如何将所有内容塞进 20 万 token 中”，而是“窗口保存*工作集*；其他所有内容都存储在磁盘上，路径由 agent 知道”。文件数量不限，跨会话和崩溃持久存在，而且——至关重要的是——可以*选择性地*重新读取。agent 会在需要时，以完全的保真度提取所需的笔记，不会出现释义衰减。

如果这听起来很像人类处理超出自身能力范围的项目的方式：没错，这就是设计模式。记忆架构值得单独写一篇文章（我已经列入计划了），但 80/20 法则其实就这么简单：把文件交给 agent，告诉它如何使用。

## 4. 背诵：破解注意力曲线

一个看似微不足道却又至关重要的技巧。让 agent 维护一个待办事项清单，并在工作进行过程中，*在最近一次输出的末尾重写清单*。由于模型最关注上下文的结尾，不断重写目标能将原本被忽略的中间部分重新拉回到焦点。Manus agent 背后的团队将此描述为有意操纵模型的注意力，而这正是目前已知解决长时间任务目标漂移问题最经济有效的方法之一。每隔几个步骤重述十行待办事项清单，比一千字的系统 prompt 更能确保目标的执行。

## 5. 即时检索：搜索优于囤积

agent 出现之前的 RAG 惯性思维是将所有信息嵌入上下文，并预先将 top-k 匹配项塞入上下文。而 agent 系统则越来越倾向于反其道而行之：保持上下文精简，并为 agent 提供*搜索工具*——然后让它在需要时立即提取所需信息。Claude Code 就是一个典型的例子：它不会索引和预加载你的代码库；它会使用 grep、glob 等关键词，打开特定文件，读取特定的 200 行代码。上下文始终保持精准。渐进式披露，而非囤积：每个搜索结果都会为下一个结果提供信息，agent 逐层构建理解，而不是在初始阶段就接收大量可能相关的文本。

成熟的解决方案通常是混合式的——前期进行一些准备工作（例如项目记忆文件、目录列表），再加上 JIT 工具处理其他所有事情。但如果拿不定主意，那就从比你感觉舒适的程度更精简的方式开始。你能掌控的检索结果比你在构建时猜测的相关性要好得多。

## 6. 隔离：子 agent 作为上下文防火墙

当子任务需要处理大量信息（例如读取整个子系统或分析这份 400 页的文档）时，父任务的窗口就会被淹没，这时就需要生成一个子 agent。子 agent 会占用一个全新的窗口进行深入分析，最终只返回一个精简后的答案。从父任务的角度来看，原本需要处理 8 万 token 的探索信息才能得出的结论最终只剩下 500 token。我在之前的 harness 文章中已经详细介绍了编排机制；这里要强调的是，多 agent 架构的核心是一种基于上下文的策略。并行性只是锦上添花，隔离性才是最终目标。

## 最后补充一条反直觉的规则：将错误保留在……

清理操作的本能——agent 失败后，用整理后的上下文重试——通常是错误的。一个能够*看到*失败尝试及其错误原因的模型会进行更新，避免重复操作；抹去证据就等于抹去了教训，恶性循环再次出现。失败的步骤应该保留在上下文中（或者至少保留在压缩后的形式，例如“尝试 X → 失败，原因是 Y”）。会话记录是本次会话的训练数据。不要对其进行清洗。

## 第四部分：案例研究

## Claude Code：信念驱动的精简

Anthropic 的编码 agent 是“精简上下文”理念最清晰的公开体现。它无需预先建立代码库索引；agent 搜索（glob、grep、定向读取）可即时拉取代码。一个 `CLAUDE.md` 记忆文件在会话启动时提供低成本、稳定的方向信息——而且由于它位于前缀中，因此对缓存友好。压缩（手动执行 `/compact` 或在接近极限时自动压缩）可保持长时间会话的运行，其 prompt 会清晰地显示决策、文件路径和未解决问题的优先级。子 agent 会处理大量占用窗口的额外任务。这六项技术全部集成在一个产品中，您今晚就可以开始学习了。

## Manus：KV Cache 学派

Manus 团队的工程笔记之所以成为必读之作，很大程度上是因为它们首先考虑了经济效益。设计时首先围绕缓存展开：稳定的前缀、仅追加历史记录、会话中不进行工具切换（仅屏蔽，不移除）。将文件系统用作无限的外部记忆——采用可恢复的压缩，这意味着只要 URL 存在，网页内容就可以从上下文中移除，因为 agent 始终可以重新获取。列出待办事项清单以引导注意力。保持故障可见，以便模型能够自我纠正。这套工具箱本质上是一样的，只是由一群盯着 token 账单的人进行调整而已。

## 百万 token 海市蜃楼

一个较为平静的案例：当超长窗口（超过 100 万 token）出现时，很多人宣称上下文工程已经过时——只需把所有东西都塞进去就行了。然而，这种做法在实际生产环境中却行不通。即使缓存了 token，成本也会随着 token 数量的增加而增长，延迟也会增加，而且由于上述上下文腐化和干扰的原因，质量在塞满 token 的窗口中反而下降了。事实证明，长窗口只是更大的画布，而不能替代对内容策划的理解。这些技术并没有变得不再重要，只是应用范围扩大了。下次当规格表暗示你的内容策划问题已经解决时，不妨记住这一点。

## 第五部分：故障模式——现场检查清单

系统 prompt 中的时间戳。一个变化的 token，缓存完全失效，账单增加 10 倍。将动态值移至工具结果中。

**包含 40 个工具的配置。**故意制造上下文混乱。仅提供最小工具集；如果需要限制，则动态屏蔽。

**囤积者的垃圾堆。** 初始阶段有 3 万个“可能相关”的信息块，其中 80% 从未被使用，所有这些都在分散注意力。应转换为即时搜索。

**释义衰减。** 层层递进的摘要，直到文件路径和约束条件发生改变。精确的标识符必须原封不动地保留在压缩过程中；高保真度的事实应该放在文件中，而不是散文摘要里。

**经过洗白的记录。**重试时会清除错误；但 agent 会重复这些错误。保持失败记录可见。

**过于简略而忽略目标。** 总结只保留了*已完成*的内容，却忽略了*尝试*的内容以及原因。始终要将客观性和开放性问题贯穿始终，并在最后重述。

**无限制的工具输出。**一个包含 2 万行文件的 `cat` 操作就会使窗口崩溃。每个工具都需要输出限制，并采用“截断后，使用偏移量读取更多内容”的约定。

## 第六部分：如何开始——一周计划

第一天：测量。提取十次最长 agent 运行的跟踪记录（可观测性文章中介绍了具体方法），并分析窗口：系统 prompt、工具、历史记录和工具结果分别占多大比例？找出占用 token 最多的前三项。没人能猜对；每个人都会对自己的分布感到惊讶。

第二天：优化经济效益。检查缓存命中率。查找前缀不稳定的原因——时间戳、请求 ID，以及历史记录之前的任何动态信息。这通常只需一行代码就能解决，而且能节省三分之一的费用。

第三天：限制工具数量。限制所有工具的输出结果；将工具结果精简到决策实际需要的程度；将工具集精简到任务所需。

第四天：添加压缩功能。编写摘要 prompt，明确列出保留/丢弃列表（决策、约束、精确路径、未解决问题与原始输出、死胡同）。压缩进度达到约 80% 时触发。在长时间任务上进行测试；与未压缩的情况进行比较。

第五天：外部化。给 agent 一份笔记文件和一份计划文件，指示其记录并重读，并添加待办事项清单。然后重新进行第一天的评估，并欣赏前后对比。

这就是整个学科的缩影。这不是框架迁移——而是一周的时间，经过深思熟虑，决定模型可以看到什么。

## 结论：注意力是一种稀缺资源

抛开一切，上下文工程是其中一种思路：**模型的智能是通过其注意力来实现的，而注意力是有限的，即使窗口很大。**你允许的每一个 token 都会与其他所有 token 竞争。prompt 工程问的是“我该如何措辞我的请求？”，而上下文工程则提出了更成熟的问题：“在我*可以*向这个模型展示的所有信息中，哪些信息最值得展示？”

这既是一项内容策划工作，也是一项经济学工作，更是一项架构工作——正因如此，它才吸收了 prompt 工程，而不是仅仅作为辅助工具。它与本系列中的其他所有内容都息息相关：harness 是这些决策的执行场所，可观测性是检验决策是否有效的方法，而上下文工程则是决策的具体内容。

这些模型将不断获得更大的上下文窗口和更精准的注意力，但这并不会让这项技术就此终结，正如更快的 CPU 从未让算法思维退出历史舞台一样。更大的容量提升了上限，而内容策划则决定了你最终能飞多接近这个上限。
