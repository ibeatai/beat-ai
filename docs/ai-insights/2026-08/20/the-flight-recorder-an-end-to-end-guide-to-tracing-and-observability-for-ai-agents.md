# 飞行记录仪：AI agent 追踪与可观测性端到端指南

你无法修复看不见的问题。如何为 LLM 应用和 agent 添加插桩、追踪和评估，并真正加以改进——从第一个 span 到生产级质量循环。

![图 1：在没有追踪和有追踪的情况下调试 agent。](https://cdn.jsdelivr.net/gh/genesislab-io/beatai-assets@5ab0231c168bc3d9d525e2de753e3f39fad885a4/ai-insights/2026-08/20/images/the-flight-recorder-an-end-to-end-guide-to-tracing-and-observability-for-ai-agents/01.webp)

不久前，我看到一个 agent 在执行一个 60 步任务的第 34 步时失败了。用户报告全文如下：“它给了我错误的文件。”

如果没有追踪，调试过程大概是这样的：重新运行任务，希望它以同样的方式失败（但实际上不会——这些系统是不确定的），盯着之前预先添加的那些打印语句，慢慢地崩溃。有了追踪，整个过程只用了大约四分钟：打开 trace，扫描 span 树，找到搜索工具返回空结果的步骤，然后看着模型——它没有说明情况——在两步之后自信地臆造出一个文件名。问题不在于模型本身，而在于某个工具返回了空的 `200 OK` 响应体，而不是模型可以响应的错误信息。

这就是本文的全部内容。我在上一篇文章中论证了模型框架与模型本身同等重要，并将可观测性比作框架的飞行记录仪。本文将深入探讨：追踪对于 LLM 系统究竟意味着什么，如何正确地为 agent 添加插桩，以及团队如何将大量 trace 转化为一台每周都能改进产品的机器。

和上一篇一样，我们将从零基础讲起，逐步深入，通过案例研究和工具概览来介绍。无需具备任何可观测性方面的经验。如果之前听说过“日志、指标和追踪”，那就太好了；如果没有，这就是第一站。

## 第一部分：基础知识

## 为什么您现有的监控系统无法发现人工智能问题

经典的可观测性发展起来是为了回答诸如以下的问题：服务是否正常运行？速度如何？错误率是多少？三大支柱——**日志**（发生了什么）、**指标**（数量/速度如何）和**追踪**（请求如何在系统中流动）——很好地回答了这些问题。

然后你发布了一个 LLM 功能，却发现出现了一种新的事件类型，而你的所有仪表盘都没有记录到。服务运行正常，延迟也正常，所有请求都返回 HTTP 200 状态码。但结果却是*错误的*——要么比上周略有恶化，要么成本翻了三倍，要么在你礼貌地询问时，系统提示信息却泄露了出来。

LLM 系统在以下四个方面打破了传统的监测假设：

1. **故障通常是语义上的，而非系统性的。** 一个幻觉答案会返回 200 状态码。一个死循环只不过是……多次成功的 API 调用。正常运行时间仪表盘显示一切正常，而产品却可能正在崩溃。
2. **它们是非确定性的。**相同的输入可能产生不同的输出，因此“在本地重现错误”（这是常规调试的基础）通常无法实现。失败运行的 trace 往往是唯一存在的证据。
3. **费用按请求计算，且波动很大。** 普通的 API 调用费用始终只有几分之一美分。而 agent 运行的费用则可能从 0.02 美元到 4.00 美元不等，具体取决于循环的执行情况。现在，费用是需要观察的运行时行为，而不是每月检查的固定项目。
4. **质量是一个分布，而非一个布尔值。** “它有效吗？”这个问题变成了“有多少比例的答案是好的，而且这个比例是否在变化？”这是一个本质上不同的问题，需要新的机制——评估——将其整合到可观测性堆栈中。

![图 2：经典的三大支柱仍然适用，但 LLM 系统增加了第四个关注点——质量——并让 trace 成为主角。](https://cdn.jsdelivr.net/gh/genesislab-io/beatai-assets@5ab0231c168bc3d9d525e2de753e3f39fad885a4/ai-insights/2026-08/20/images/the-flight-recorder-an-end-to-end-guide-to-tracing-and-observability-for-ai-agents/02.webp)

## 为什么 trace 会成为主角

对于无状态微服务，指标通常是主要观察视角，而 trace 则用于处理特殊情况。但对于 agent 来说，情况恰恰相反。Agent 的运行*就是*一个故事：计划、调用工具、读取结果、调整、调用另一个工具、从错误中恢复、生成答案。指标对这个故事的概括很差。日志将其分散在上千行数据中。而 trace 则完整地保留了整个因果链，按顺序排列，并包含时间信息。

所以，这篇文章可以用一句话概括：**对 agent 进行插桩，使每次运行都能生成完整、易读的 trace；然后基于这些 trace 构建质量、成本和调试工作流程。**其他一切都是详细说明。

## 第二部分：Agent trace 的构造

这里介绍一些术语，因为整个领域都离不开它们。**Trace** 记录了一次端到端运行（一次用户请求，一次 agent 任务）。Trace 包含 **span**——按时间顺序排列的操作，构成父子树结构。以上内容符合 OpenTelemetry 的标准，OpenTelemetry 是统一遥测数据发送和收集方式的开放标准。

LLM 系统的新特点是*哪些类型的 span* 会出现，以及*它们必须承载哪些内容*才能发挥作用。

![图 3：单个 agent 运行形成 span 树——生成、工具调用和检索嵌套在运行之下。](https://cdn.jsdelivr.net/gh/genesislab-io/beatai-assets@5ab0231c168bc3d9d525e2de753e3f39fad885a4/ai-insights/2026-08/20/images/the-flight-recorder-an-end-to-end-guide-to-tracing-and-observability-for-ai-agents/03.webp)

**生成 span** 记录模型调用，它们是核心所在。一个有效的生成 span 应包含模型名称和参数、完整的输入（系统 prompt + 消息）、完整的输出、token 计数（输入、输出、缓存）、计算成本、延迟以及完成原因。如果忽略这些信息，在最需要它们的时候——也就是事件处理过程中——你会后悔莫及。

**工具 span** 记录工具/函数的执行过程：名称、参数、结果（或错误）、持续时间。我之前提到的空结果错误就是在工具 span 中发现的。在 agent 调试中，工具 span 往往是隐藏问题的关键所在，因为工具是现实世界各种复杂因素进入系统的地方。

**检索 span** 记录了 RAG 查找过程：查询、检索到的内容块、相似度得分、源文档。当用户反映“它从错误的文档中返回了结果”时，此 span 会解释原因。

Trace 之上是**会话**（或线程）：多轮对话会将多个 trace 分组，以便跟踪用户的完整交互过程。所有 trace 的下方和周围是**元数据**：用户 ID、会话 ID、prompt 版本、模型版本、功能标志、环境以及自由格式的**标签**。元数据在最初看来是可选的；但正是它使得 trace 在第九十天后仍然可以查询（例如，“显示企业用户在 prompt v14 上的所有失败运行”）。

两条值得注意的标准化要点。**OpenTelemetry GenAI 语义约定** 为上述所有内容（例如 `gen_ai.usage.input_tokens` 等）定义了标准属性名称，这意味着您只需进行一次配置，即可在不同的后端之间轻松移植。而且，大多数 LLM 可观测性工具现在都支持或可以接收 OTel 数据，因此“选择哪个供应商？”这个问题不再像以前那样受到限制。请使用标准名称。未来的你会感谢我的。

## “好”是什么样子的

当你能够打开任何生产运行记录并在 1 分钟内回答以下问题时，你就知道你的追踪是正确的：用户实际提出了什么问题？模型在每个步骤中看到了什么——是完整的提示信息，而不是截断的提示信息？每个工具返回了什么？token 和资金都去了哪里？以及在哪个具体步骤出现了问题？

如果其中任何一项需要通过 SSH 连接到某个地方，或者需要按时间戳关联三个日志文件，那么检测工作还没有完成。

## 第三部分：轻松完成插桩

## 先采用自动插桩，再手动处理关键之处

这个领域里所有严肃的工具都内置了集成功能，可以对接流行的 SDK 和框架（例如 OpenAI/Anthropic 客户端、LangChain、LlamaIndex、Vercel AI SDK 等），并自动捕获生成 span。从这里入手；只需一行代码，就能获得 80% 的价值。

剩下的 20% 是对自身逻辑的手动插桩：封装工具函数、检索步骤和 agent 循环迭代，使 trace 树反映架构，而不仅仅是模型调用的扁平列表。大多数 SDK 都将其实现为装饰器或上下文管理器：

```python
@observe()                       
def search_codebase(query: str):
    results = index.search(query)
    if not results:
        raise ToolError("no matches — try a broader query")   
    return results
```

`ToolError` 的重要性体现在两个方面：模型可以在会话期间对其做出反应，并且在 trace 中会显示为一个正确的失败 span，而不是一个静默的空成功。插桩和框架设计就这样不断地相互促进。

## 不要采样。真的。

在经典的可观测性中，采样是生存的必要条件——没有人会存储每秒 5 万次请求的所有 trace。LLM 应用的运行流量通常远低于此，因此每个 trace 的价值都大大增加（记住，它是无法复现行为的唯一证据）。经济学原理反过来：除非规模非常大，否则**应该保留 100% 的 trace**；即使规模很大，也应该只对成功的事件进行采样，而不要对失败的事件进行采样。

## 存储前先做脱敏

全保真追踪意味着用户数据会存储在您的可观测性后端。这既是优势（您无法调试看不到的数据），也是风险（个人身份信息、机密信息、受监管数据）。生产环境会在 SDK 层进行数据脱敏处理，然后再发布任何内容：屏蔽电子邮件地址、电话号码、信用卡信息和 API 密钥；对用户 ID 进行哈希处理；对于要求最严格的环境，建议自行托管后端（这也是开源方案在金融科技和医疗保健领域广受欢迎的原因之一）。务必在第一天就做出决定。在合规性审查之后再进行数据脱敏处理，将会是一场灾难。

## 版本控制所有影响行为的因素

追踪信息回答的是“发生了什么”。要回答“哪些*改变了*”，每条追踪信息都必须包含影响行为的各种因素的版本信息：提示版本、模型版本、工具模式版本、检索索引版本。以这种方式标记追踪信息的团队可以通过查询来回答“质量下降是否始于提示版本 v15？”。而没有标记追踪信息的团队则只能通过考古学来寻找答案。

## 第四部分：从观察到改进——质量循环

这就是区分仅仅拥有可观测性的团队和能够从中获得复利收益的团队的关键所在。单凭追踪数据就像一面后视镜。制胜之道在于循环往复：

![图 4：循环——生产 trace 生成数据集，数据集支持评估，评估为变更把关，变更得以放心发布，然后重复。](https://cdn.jsdelivr.net/gh/genesislab-io/beatai-assets@5ab0231c168bc3d9d525e2de753e3f39fad885a4/ai-insights/2026-08/20/images/the-flight-recorder-an-end-to-end-guide-to-tracing-and-observability-for-ai-agents/04.webp)

**第一步：对生产 trace 进行分类。**养成每日或每周的习惯：审查失败的运行、被否决的答案、成本异常值以及最慢的 trace。大多数工具都支持评分和注释，因此人工可以直接在 trace 上标记运行失败的*原因*。

**步骤 2：将错误 trace 转化为数据集项。**每一个值得关注的故障都会成为一个测试用例：触发故障的输入加上对正常情况的定义。这是 LLM 工程中最有效的习惯，而且在大多数平台上只需一个“添加到数据集”按钮即可实现。评估套件不再是人为构造的示例，而是系统所有真实故障方式的精简记录。

**步骤 3：对数据集运行评估。** 一些检查是代码层面的（输出是否解析？引用的文件是否存在？是否在预算范围内？）。更模糊的特质——例如实用性、相关性、语气——则使用**LLM 作为评判者**：第二个模型会根据评分标准对输出进行评分。评判者并非完美无缺，需要偶尔与人工标注进行校准，但它们具有一致性、不知疲倦且成本足够低，可以对每次更改都运行一次。

**步骤 4：评估变更的门控机制。** 新提示、新模型、新工具描述？先运行测试套件，与基线进行比较，只有通过测试才能发布。这是行为的持续集成/持续交付 (CI/CD)，它将模型升级从盲目尝试转化为可读的差异分析。

**步骤 5：持续监控生产环境。** 在线评估能够近乎实时地对部分实时流量进行评分，捕捉到任何预发布测试都无法发现的问题：模型提供商悄悄更新行为、新用户群体涌入、依赖项性能下降等等。一旦出现质量评分下降、单次会话成本飙升、延迟增加和错误率异常——即 LLM 事件的四大罪魁祸首——就应立即发出警报。

注意发生了什么：可观测性不再仅仅是调试工具，而是成为了改进过程的引擎。这就是最终目标。

## 第五部分：高级主题

**多 agent 追踪。**当编排器生成子 agent 时，trace 会形成一棵深树——子 agent 运行嵌套在父 agent 内部，每个子 agent 都有自己的生成调用和工具。两件事至关重要：上下文传播（子 span 必须携带父 agent 的 trace ID，如果通过 OTel 连接，OTel 会自动处理）和*可读性*——一棵包含 400 个 span 的树需要能够折叠、汇总每个分支的成本以及提供摘要视图，否则没人会打开它。Anthropic 在撰写其多 agent 研究系统时，认为完整的生产环境追踪是使非确定性多 agent 调试变得可行的关键。我曾调试过使用和不使用这种追踪的多 agent 系统：相信他们。

**长时间运行的异步 agent。**一个 agent 运行一小时，设置检查点，崩溃后恢复运行，然后要到第二天才能完成，这种做法破坏了简洁的请求-响应 trace 模型。可行的模式是：将每个片段视为独立的 trace，通过共享的运行 ID 进行链接，并明确设置检查点/恢复事件。虽然这种方式比较繁琐，但它既能让工具保持良好运行状态，又能让人清楚所处的位置。

**可查询的故障特征。**借助良好的 trace，agent 的异常行为不再是模糊的迹象，而是可检测的模式。恶性循环是指连续 N 次使用相同参数调用同一工具。上下文腐化表现为质量分数随 trace 深度的增加而下降。工具混淆表现为 schema 更改后特定工具的重试率过高。成熟的团队会将这些特征编码为已保存的查询和警报，从而将上个季度的神秘事件转化为下个季度的自动化检测。

**成本归因和单位经济效益分析。**一旦每个 span 都包含 token 计数和成本，就可以按功能、用户级别、prompt 版本进行聚合，最终回答诸如“平均一次支持对话的成本是多少？哪 2% 的对话消耗了 40% 的成本？”之类的问题。我曾亲眼目睹，仅仅一个下午的成本追踪分析，就通过发现一个每晚默默重新嵌入整个文档语料库的重试循环，收回了整个可观测性堆栈的成本。

**回放和时间旅行调试。**由于生成 span 存储了完整的输入，可以调整 prompt 或使用不同的模型重新运行任何步骤，并比较结果——将“我认为更改 prompt 可以解决问题”的想法变成一个只需 30 秒的实验。这是第一次使用时感觉最神奇的可观测性功能。

## 第六部分：案例研究

## 午餐前花费 400 美元的厄运循环

我认识的一个团队连夜运行了一个数据增强代理，处理了几千条记录。第三方 API 更改了错误格式；代理的工具封装器吞掉了新的错误格式，返回了一个空字符串；模型因为找不到任何有用的信息，就一直重试。一直重试到天荒地老。正常运行时间仪表盘显示：绿色。第二天早上的账单：却显示：绿色。

修复只用了十分钟，*因为有追踪记录*：跨度树显示相同的工具调用重复出现，被吞掉的错误在工具的原始输出中清晰可见，并且包装器也得到了修复，可以正确抛出异常。真正起到持久作用的是他们添加的警报：“同一工具 + 相同参数在同一追踪中出现 5 次以上 → 通知相关人员。” 这就是可观测性成熟度曲线的缩影——事件、诊断，然后是可查询的特征码，这样就不会再出现意外情况了。

## 客服机器人变差了，却没做任何改变。

两周内，客服机器人的差评率悄然上升。没有进行任何部署，也没有立即进行任何更改。在线评估发现，差评率下降的源头在于引用知识库的答案；检索范围显示相似度评分悄然下降；原因是内容团队将帮助文章迁移到一种新的格式，而这种格式的分块处理效果很差。即使仔细查看应用程序日志也无法发现这个问题，因为没有任何*故障*——每个组件都在处理略有错误的数据，并且运行正常。只有跨平台可见性才能发现这类错误。

## 评估套件作为升级降落伞

当重大模型升级上线时，拥有完善流程的团队会在当天下午用他们积累的评估套件（数百个从真实生产环境中收集的失败案例）对新模型进行测试。有时结果是“全面升级，质量提升 8%”。有时结果是“升级摘要器，暂停提取流程——日期方面出现倒退”。无论哪种情况，都是在数小时内根据证据做出决策，而不是像我之前见过的那样：凭感觉升级，一周后从愤怒的用户那里发现倒退，然后慌忙回滚。

## 第七部分：工具概览

这个领域发展迅速。截至 2026 年，主要的投资选项大致如下：

- **LangSmith**（LangChain）。成熟的 SaaS 解决方案；深度集成 LangChain/LangGraph；强大的评估和注释队列。*最适合：LangChain 生态系统中的团队。*
- **Langfuse**（开源）。可自托管，OTel 原生支持，提供完整的循环功能（跟踪、评估、提示管理）；提供慷慨的免费套餐。*最适合：需要控制权/数据驻留的团队。*
- **Braintrust**（Braintrust）。秉持“评估优先”的理念；实验和持续集成（CI）门控是其核心工作流程。*最适合：将评估视为产品的团队。*
- **Arize Phoenix**（开源）。原生支持 OTel，具备强大的检索/嵌入分析能力，并传承了机器学习可观测性技术。*最适合：RAG 数据密集型系统，以及漂移分析。*
- **W&B Weave**（Weights & Biases）。实验追踪基因；在机器学习运行旁提供追踪和评估结果。*最适合：已在使用 W&B 的团队。*
- **Helicone**（开源）。基于代理：只需更改一个 URL 即可控制所有操作；支持缓存和速率限制。*最佳选择：启动速度最快，支持网关控制。*
- **Datadog / Grafana LLM 观察**（现有解决方案）。LLM 跟踪集成到您现有的 APM 系统中，实现统一管理。*最适合：已采用标准化 APM 的组织。*
- **OpenTelemetry GenAI**（标准）。并非产品，而是底层架构和语义约定。*最适合：所有人，作为检测层。*

我的建议与那篇关于工具的文章不谋而合：关键不在于工具本身，而在于循环。选择符合你自身限制条件（自托管需求、现有技术栈、框架）的工具，并遵循 OTel 的规范以确保其可移植性，然后将节省下来的决策精力投入到实际的跟踪分析和数据集构建中。一个平庸但每天都在使用的工具，胜过一个完美却无人问津的工具。

## 第八部分：失效模式——可观测性努力如何失败

**只写可观测性。** 所有数据都已接入监控，但无人审核。痕迹堆积如山，如同无人观看的监控录像。解决方法：每周固定一次——30 分钟，筛选出最糟糕的 10 条痕迹，轮流进行。

**难以理解的跟踪记录。** 600 个跨度，结构混乱，提示信息被截断。技术上完整，但实际上毫无用处。解决方法：对你的*架构*（代理步骤、工具、检索）进行检测，而不仅仅是 API 调用，并且永远不要截断输入。

**个人身份信息泄露事件**。在一次安全审查中，我们发现第三方后端存储了长达六个月的原始用户数据。解决方案：从一开始就在 SDK 中进行数据脱敏处理；如果数据确实需要，则选择自行托管。

**评估剧场**。这是一套由 20 个精心设计的测试用例组成的体系，这些用例总是能通过，但与任何结果都没有关联。解决方法：从实际制作失败案例而非凭空想象中构建数据集，并按季度对评判者进行人工标注校准。

**成本盲点，却拥有完美追踪。** 令牌被记录在各处，却无人汇总，直到财务部门转发发票时，人们才第一次注意到这个问题。解决方案：按功能和会话汇总成本，并对趋势而非总成本发出警报。

**仪表盘坟场。** 第一周就建了十二个仪表盘；唯一真正重要的——按版本划分的质量评分随时间变化的仪表盘——却从未建成。解决方法：从最能引起人们关注的四个问题入手（质量下降？成本飙升？延迟增加？错误异常？），并针对这些问题建立仪表盘。其余的都可以毫不犹豫地删除。

## 第九部分：如何开始（本周开始，而非本季度）

第一天：选择一个工具，并为流量最高的 LLM 功能启用自动插桩。通常只需一行代码。确认跟踪数据正常流动。

第二天：手动添加工具和检索相关的跨度，使跟踪树与你对系统的理解模型相符。添加元数据：用户 ID、会话、提示符版本。

第三天：完整阅读十条生产环境跟踪日志。不是看仪表盘，而是阅读实际的跟踪日志。我保证你至少会发现一件让你震惊的事。（每个人都会发现。通常是某个提示信息与你预想的不符，或者某个工具在 15% 的调用中悄无声息地失败。）

第四天：根据你找到的五个最糟糕的跟踪记录创建一个数据集。为它们编写评估报告——尽可能进行代码检查，如果无法进行代码检查，则由 LLM 评审员使用书面评分标准进行评估。

第五天：将评估结果连接到 CI，以便在下次提示更改时运行，并设置一个警报：每次跟踪的成本，高于七天平均值三个标准差。

一周之内就能建立一个运转良好的质量控制循环。虽然规模不大，但却是实实在在的——而且这种循环还会不断累积，因为未来的每一次失败都会被记录下来，最终汇入数据集，不断增强整个系统，永无止境。

## 结论：后视镜驱动汽车

人们很容易将可观测性归类为“运维”——安装好就不用管了。但对于人工智能系统而言，我认为这种思维模式完全错误。因为人工智能系统中的故障是语义上的，传统监控手段无法察觉，而且本质上无法复现，所以追踪存档根本不是后视镜。它是产品改进的原材料：每个数据集条目、每一次评估、每一次模型升级，以及每一次“我们比用户更早发现问题”的时刻，都可追溯到（抱歉）早期搭建的监控系统以及真正分析其捕获数据的团队。

在之前的文章中，我将可观测性列为七个器官之一。而这次的深度分析让我意识到：它是让其他所有器官都得以改进的关键器官。能够自我感知的系统，才是可以有意识地改进，而不是靠偶然因素改进的系统。

发动机就是模型，汽车就是框架。它集仪表盘、黑匣子和技师诊断接口于一体——没有它，汽车很难完成比赛。
