# Agent 的经济学：token 计费、缓存和路由

你的 agent 没有性能问题，而是有单位经济效益问题——解决之道在于工程设计，而非增加预算。

![图 01：钱都花到哪儿去了](https://cdn.jsdelivr.net/gh/genesislab-io/beatai-assets@a82e2f886e76d0cda482d969a600732094cdd406/ai-insights/2026-08/20/images/the-economics-of-agents-token-accounting-caching-and-routing/01.webp)

每个构建 agent 的团队最终都会遇到这样一个时刻。我开始把它称为“发票时刻”。

演示版成本 11 美分，大家都很喜欢。你先发布了试点版，然后是测试版，接着引入真实流量——结果财务部门发来月度账单，主题只有一个问号。一切正常：没有事故，没有宕机，也没有客户投诉。agent 只是把你设定的任务原样执行了一万次，结果发现，这套系统每次任务的成本比任何人预想的都要高出四十倍。

这是系列文章的第四部分。在 [harness](https://medium.com/towards-artificial-intelligence/the-harness-is-the-product-an-end-to-end-guide-to-harnessing-in-agentic-ai-fcc0a9931526) 这篇文章中，我论证了模型本身并非产品，围绕模型构建的 harness 才是。在 [observability](https://medium.com/towards-artificial-intelligence/the-flight-recorder-an-end-to-end-guide-to-tracing-and-observability-for-ai-agents-1906c4212826) 这篇文章中，我们构建了一个飞行记录器，它可以记录 agent 实际执行的操作。在[上下文工程文章](https://medium.com/towards-artificial-intelligence/context-engineering-the-discipline-that-quietly-replaced-prompt-engineering-da39172dbe15)中，我们将上下文窗口视为一种稀缺资源并对其进行管理。本文将探讨另一种稀缺资源：资金。我们将讨论 token 记账、prompt 缓存、模型路由以及决定你的 agent 是产品还是昂贵爱好的单位经济效益。

好消息，也是本文的核心论点：agent 成本不是天气，不是只能被动承受的事。成本是 harness 的一项工程属性，像延迟一样可调。然而，大多数团队却白白浪费了 60% 到 90% 的支出，因为没有人真正负责这部分成本。

让我们从零开始构建思维模型。

## Token 计费入门：计量表究竟在哪里运转

每次 LLM 调用都根据两个指标计费：输入 token（发送的所有内容）和输出 token（模型生成的所有内容）。输出 token 的单价更高——通常是输入 token 的 3 到 5 倍——这几乎导致所有人得出第一个错误结论：真正花钱的是输出。

对于聊天机器人来说，有时会这样。对于 agent 来说，几乎从不会。**Agent 是输入主导型系统**，理解其中的原因正是本文最重要的观点。

机制如下：agent 运行一个循环——与我们在 harness 文章中绘制的循环相同：模型查看上下文，选择一个工具，工具返回结果，结果被追加到对话中，如此循环往复。关键在于“追加”二字。LLM API 是无状态的。每一轮，都要重新发送截至当前的整段对话——系统 prompt、工具定义、之前所有工具返回的结果、之前所有模型回复。第 12 轮的成本并非来自第 12 轮新增的内容。第 12 轮的成本是*之前所有信息*的重新发送和计费，作为新的输入。

以一个普通支持型 agent 为例来算算账。假设系统 prompt 需要 2,000 个 token，工具 schema 需要 3,000 个 token，每个回合大约会增加 1,800 个 token 的工具结果和模型输出，一个典型的任务需要 12 个回合。第一回合发送 5,000 个 token，第二回合发送 6,800 个，第三回合发送 8,600 个。到第 12 个回合，需要发送超过 24,000 个 token 才能生成一个 300 token 的回复。把整个任务的输入 token 加起来，大约计费 **180,000 个输入 token**，而输出 token 甚至不到 4,000 个。

Agent 对话的成本并不会随回合数线性增长。它大致与回合数的平方成正比，因为每一次新回合都要重新支付之前所有回合的成本。我称之为“agent 税”，这也是为什么聊天机器人领域中按 token 计费的直觉在这里完全失效：

> *聊天产品的成本取决于用户说了多少。Agent 的成本则取决于 agent 思考了多少——每次循环迭代都会以全价重新读取整份记录。*

按实际价格计算——比如每百万个输入 token 3 美元，每百万个输出 token 15 美元（具体数字可能会有所波动，但这个比例已经稳定了一段时间）——一个 12 轮的任务，输入成本大约是 54 美分，输出成本大约是 5 美分。输入成本占总成本的 90%。如果每月有 10 万个任务，总成本将达到 5.9 万美元，而解决办法并非“使用更便宜的模型”。至少现在还不行。解决办法是停止为同样的 token 一遍又一遍地支付全价。

这就引出了一个值得我们在进行任何优化之前就借鉴的记账习惯。

## 账本：每次调用记五个数，否则就当没发生

你无法优化只做汇总记账的东西。月度账单告诉你存在问题，但无法告诉你问题*出在哪里*。解决方案在于账本，而账本的存放位置就是你在第二篇文章中已经构建的追踪基础设施——每次模型调用都是一个 span，每个 span 都应该包含五个数字：

**输入 token、缓存读取 token、缓存写入 token、输出 token 和思考 token。** 这五种 token 都会在 API 响应中返回；只需要停止丢弃它们。基于这些 token，其他一切都只是简单的算术运算。有效输入价格是支出除以输入量——这个数字可以告诉你缓存是否真正有效。每个任务的调用次数可以捕捉到单次调用指标所隐藏的重试风暴。如果绘制对话中每一轮的成本，图形应该像一道阶梯；如果看起来像曲棍球杆，说明上下文正在膨胀（第三篇文章的问题），而你的钱包正在为此付出代价（本文的问题）。

两条会计规则能避免很多麻烦。首先，**将成本归因于任务，而非调用**——每个 span 都绑定一个任务 ID，这样只需一次查询就能了解 40 美元的异常值背后的全部情况。其次，**在边缘定价，以 token 记录**。价格会变动，模型会更换，协商折扣也会出现。如果账本存储 token 并在读取时应用价格，所有历史记录都具有可比性。直接记录美元的团队最终无法判断三月份是效率提高了，还是供应商降价了。

这在 harness 中只要二十行代码，却能将本文剩余部分的每个论点从观点变成图表。

> *发票就像尸检报告，账本就像心电图仪。你应该关注的是后者。*

现在，让我们来谈谈业内最容易被误解的折扣。

## Prompt 缓存：大多数团队都会意外配置的 90% 折扣

![图 02：缓存经济学——稳定前缀与不稳定后缀](https://cdn.jsdelivr.net/gh/genesislab-io/beatai-assets@a82e2f886e76d0cda482d969a600732094cdd406/ai-insights/2026-08/20/images/the-economics-of-agents-token-accounting-caching-and-routing/02.webp)

在上下文工程文章中，我们了解了 KV 缓存：提供商会保留模型对 prompt 前缀的内部计算结果，这样，如果下一个请求以*完全相同的字节*开头，就不需要重新计算该前缀。我当时略过了定价。缓存的输入 token 通常按未缓存 token 价格的**十分之一左右**计费。写入缓存通常会略微增加费用——大约比基础输入价高 25%——而读取操作相比之下几乎是免费的。

戴上会计帽再读一遍。Agent 账单中最大的单项——重新发送的输入——享有官方认可的 90% 折扣，唯一的条件是*前缀逐字节稳定*。这就是为什么当有人给我看一张吓人的账单时，我首先要问的是缓存命中率，而不是模型选择。

游戏规则直接源于缓存机制的运作方式：

**缓存匹配前缀，只要一个字节变化，其后的所有内容都会失效。** 你的 prompt 是一个堆栈：系统 prompt，然后是工具定义，再然后是对话历史记录，最后是最新回合。任何会变化的内容都必须尽可能地放在堆栈深处。稳定的内容排在最前，易变的内容排在最后。

**时间戳反模式会吃掉你的所有折扣。** 系统 prompt 顶部的 `Current time: 14:32:07` 行每次请求都会变，这意味着前缀永远不会匹配，缓存命中率为零，你将永远在全价之外额外支付写入溢价。如果模型需要时间，请将其放在最新消息中或通过工具提供。（我们在第三篇文章中将其作为上下文问题讨论过；但它实际上是一个更大的成本问题。）

**历史记录必须仅追加。** 如果 harness 在回合之间重写、重新排序或“清理”先前的消息，每个回合都会导致缓存未命中。这也是为什么工具需要遵循“屏蔽，不要移除”规则的原因：在对话过程中将工具 schema 从定义块中移除，会导致前缀失效。请改用 logits 或指令来禁用它。

**工具 schema 是前缀的一部分。** 根据请求动态组装不同的工具集看似巧妙，但实际账单却会非常昂贵。请保持会话内工具集的稳定性。

**注意 TTL。** 缓存会过期——通常在几分钟不活动后就会过期，某些服务商提供付费延长缓存的服务。如果一个人每 40 秒回复一次 agent，就能保持缓存预热。如果他离开去喝咖啡，回来时就会遇到冷前缀，需要支付全价。对于长时间运行的后台 agent，专门设计循环、让请求在缓存窗口内发出，可能确实值得。

在完全信任它之前，务必做好检测。提供商会在 API 响应中返回缓存统计信息——例如 `cache_read_input_tokens` 等——而你的跟踪（参见第二篇文章）应该在每个 span 中记录它们。关键指标是**有效输入价格**：总输入支出除以总输入 token 数。如果混合费率没有显著低于标价，那么前缀中肯定有内容在变。比较两个连续请求的差异，通常就能找到那个导致每月花费五位数的时间戳、请求 ID 或随机排序的工具列表。

回到我们的支持型 agent：同样的 18 万个输入 token，但由于前缀稳定且缓存已预热，其中约 90% 的 token 计费价格只有原来的十分之一。原本 54 美分的输入成本降至约 10 美分。Agent 的行为没有任何改变，也没有人做 prompt engineering。我们只是停止了重复购买相同的 token——总账单缩减了 4 倍，这在所有演示中都无法察觉，但对损益表却至关重要。

![动画：成本计时器——同一任务，有缓存和无缓存两种情况](https://cdn.jsdelivr.net/gh/genesislab-io/beatai-assets@a82e2f886e76d0cda482d969a600732094cdd406/ai-insights/2026-08/20/images/the-economics-of-agents-token-accounting-caching-and-routing/03.webp)

缓存机制就像是可预测性带来的折扣。下一个杠杆则是如实告知每一步实际难度所带来的折扣。

## 模型路由：停止派外科医生去倒垃圾

![图 03：路由级联 — 路由和级联模式](https://cdn.jsdelivr.net/gh/genesislab-io/beatai-assets@a82e2f886e76d0cda482d969a600732094cdd406/ai-insights/2026-08/20/images/the-economics-of-agents-token-accounting-caching-and-routing/04.webp)

在你的 agent 流程中，有一个步骤会判断用户邮件中是否提及退款。如果你和大多数团队一样，那么做出这个“是/否”判断的模型，正是负责多步骤规划的那个前沿模型——而这个模型的成本比那种能十次十次都准确完成这项任务的小型快速模型要高出一个数量级。

前沿模型的价格是小型模型的 10 到 60 倍，而“所需性能”与“实际支付的性能”之间的差距纯粹是利润流失。路由是指将每次调用匹配到能够执行该调用的最便宜的模型。以下三种模式按复杂程度递增的顺序排列：

**按步骤类型进行静态路由。** 最简单也最容易被低估的方法。查看您的 agent 的调用流程，并为每个调用环节添加标签：规划、工具选择、提取、摘要、格式化、验证。规划和最终验证环节保留在强模型中。提取、分类、压缩摘要、标题生成和格式化环节则移至小模型。无需机器学习，也无需路由服务——只需在您已有的调用环节上添加一个 if 语句即可。大多数团队可以将 30-50% 的调用转为这种路由方式，而不会察觉到任何质量差异，因为对于机械步骤而言，质量差异并不存在。

**按难度动态路由。** 一个低成本的分类器（或小型模型本身）对传入的任务进行评分并进行路由：简单的任务分配给小型模型，复杂的任务分配给前沿模型。路由文献大多基于此，但请注意——一个需要独立评估套件、独立监控和独立值班的路由系统，只有规模足够大的系统才能负担得起。因此，建议先采用静态路由。

**级联策略。** 先尝试低成本模型。验证其结果——可以使用验证器、schema 检查或强模型抽查。仅在失败时才升级模型。以下计算结果令人震惊：假设小型模型的价格是大型模型的十分之一，成功率为 70%。每次尝试需要支付 1 个单位，而升级的 30% 的尝试则需要额外支付 10 个单位：0.7 × 1 + 0.3 × 11 = 平均 4 个单位，而将所有尝试都发送到大型模型则需要 10 个单位——**即使低成本模型失败率接近三分之一，成本也降低了 60%**。即使重试次数翻倍，成本降低 10 倍的模型仍然比大型模型便宜 5 倍。

级联算法存在失效模式，而且这些模式值得命名，因为团队发现它们的成本很高。验证并非免费——如果检查低成本答案的成本与生成高成本答案的成本相同，那么级联算法就会失效。延迟会不断累积——级联算法是串行的，而面向用户的 agent 可能没有足够的时间预算。而那些*漏过*验证的错误是最糟糕的，因为你优化的恰恰是检查器无法发现的那些故障。级联算法适用于验证成本低且客观的情况：例如，经过 schema 验证的提取、需要编译的代码以及可以与源文件进行比对的答案。它们不适用于开放式的判断决策。

还有一条比上述所有规则都更重要的路由规则：**路由推理工作量，而不仅仅是模型**。现代模型会消耗“思考”token——记住，这些 token 是按输出计费的，而且费用很高——并且思考深度通常是每次调用都可以配置的。在格式化步骤中分配推理预算无异于浪费金钱。你为静态路由创建的步骤类型标签可以告诉你哪些地方需要思考（规划、验证），哪些地方不需要思考（其他所有地方）。

## 多 agent 乘数

关于 harness 的文章从架构的角度探讨了多 agent 编排；其经济性问题值得单独成段讨论，因为数字非常惊人。单个 agent 消耗的 token 数量大约是聊天交互的 4 倍。多 agent 系统——编排器向子 agent 分发任务——的消耗量约为 15 倍。每个子 agent 都需要支付系统 prompt 和工具的准入费用，编排器需要支付将上下文序列化给 worker 以及读取其报告的费用，而且根据定义，并行分支无法共享 KV 缓存。

这并非否定多 agent 方案，而是说明它需要额外投入。上下文隔离（正如我们在第一篇文章中提到的，这才是多 agent 方案真正奏效的原因）有时能带来 15 倍的性能提升——例如，某些研究任务的耗时远超单个上下文窗口，或者某些迁移任务需要并行处理以节省实际运行时间。但“看起来更智能”并不能成为 15 倍性能提升的理由。我的原则是：子 agent 必须有充分的理由才能获得系统 prompt。如果一个工作进程只需要调用一次工具并返回结果，那就应该将其内联。

## 单位经济效益：计算每项任务的成本，否则你就是在盲目行事。

![图 04：单位经济效益——P95 的末日循环](https://cdn.jsdelivr.net/gh/genesislab-io/beatai-assets@a82e2f886e76d0cda482d969a600732094cdd406/ai-insights/2026-08/20/images/the-economics-of-agents-token-accounting-caching-and-routing/05.webp)

目前为止，所有措施都旨在优化调用成本。企业购买的不是调用次数，而是最终成果。真正重要的单位是**每完成一项任务的成本**——例如，每解决一个工单、每合并一个 PR、每完成一份研究简报——而且这个数字的分布比它的平均值更重要。

agent 任务成本呈现极其严重的长尾分布。支持工单的中位数成本可能只有 8 美分，而 p95 却要 4 美元，p99 更是高达 40 美元，因为 p99 是一个陷入死循环的 agent——它不断地以略微不同的方式重试失败的工具，反复读取同一个文件，在成本不断攀升的循环中自我道歉。我们在可观测性文章中已经将死循环视为一种故障特征。在账本中，它们看起来是这样的：**1% 的任务悄无声息地消耗了你三分之一的预算。**平均值完全掩盖了这一点。如果你要追踪一个成本图表，那就用百分位数图表。

这些防御措施都是 harness 的特性，这一点现在应该已经成为本系列文章反复强调的主题：

**预算和断路器。** 每个任务都有一个 token 预算和回合上限，由 harness 强制执行，而非只向模型提出建议。超出预算是一类明确结果：停止，设置检查点（第一篇文章的持久执行机制），然后要么优雅降级，要么通知人工干预。Agent 的超支无法超过上限后，p99 就会从一起事故变成一个账单条目。

**通过追踪进行成本归因。** 您的飞行记录器已经记录了每个 span 的 token。将它们汇总起来：每个任务、每个工具、每个模型、每个客户、每个功能的成本。我保证，您第一次看到汇总结果时，会有一些令您惊讶的地方——一个“快速查找”工具返回了 30,000 个 token 的响应，一个企业客户的工作流程成本是其套餐价格的 20 倍，一个重试策略导致您的预算遭受 DDoS 攻击。在第二篇文章中，我将成本称为财务部门首先发现的可观测性特征；在这里，您可以将其转化为仪表板，而不是事后分析。

**利润率计算，已记录在案。** 当每个任务的成本乘以每个结果的任务数远低于结果的价值时，agent 就可行——并且要留有余地。如果一个已解决的工单节省了 6 美元的人工时间，那么 0.40 美元的 agent 综合成本就是一笔不错的生意；而 3 美元的成本则更像是一项科学研究。明确目标，并将回归问题视为延迟回归问题：二分查找、找出原因、修复。

而成本最低的任务就是：不运行它。对重复请求进行去重，缓存*结果*（而不仅仅是 prompt——如果十个用户询问同一个故障，agent 只需查询一次），并让简单的代码绕过 agent 处理那 20% 可以通过正则表达式或数据库查询解答的请求。查询订单状态最昂贵的方法，莫过于请求一个前沿模型来完成。

## 高级货架：批量生产、饮食控制以及自制与购买的陷阱

有些杠杆指标虽然难以归类，但却会出现在每个成熟 agent 的损益表中：

**批量 API。** 大多数供应商提供的是异步处理——一天内即可获得结果，通常价格只有**一半**。agent 有大量非交互式工作：例如夜间评估运行（第二篇文章中的 CI/CD 循环）、数据回填、报告生成、记忆整合以及 embedding 刷新。将可批量处理的工作迁移到批量处理相当于享受了 50% 的折扣，但这需要队列和一些耐心，团队通常会发现他们三分之一的工作量都符合条件。

**输出优化。** 输出 token 是单位成本最高的资源，而 agent 常常将它们浪费在繁文缛节上：重述计划、道歉、用文字包装 JSON 数据。结构化的输出，例如严格的模式、简洁的格式指令、停止序列以及每个调用点的最大 token 限制，都能有效减少输出 token。通常，输出成本可以降低 20% 到 30%——虽然比输入端的收益要小，但它确实能降低延迟，而用户能真切地感受到这种变化。

**压缩也是有代价的。** 第三条规则中的压缩过程——总结历史记录以恢复上下文——本身就是一个 LLM 调用，而简单地“每回合都压缩”的策略可能会付出比它节省的 token 更多的代价。在小模型中，应在达到阈值时进行压缩，并且要记住压缩会重置缓存前缀——将其视为一项资本支出并进行合理安排。

**自托管，一个永恒的陷阱。** 在每个规划周期中，总会有人提议运行开放权重模型“以节省成本”。有时这确实没错——在持续、可预测的高流量情况下，或者在数据驻留受限的情况下。但你用来比较的 API 价格包含了别人的 GPU 和资源利用率，而你实际的替代成本则包括闲置容量、推理堆栈以及现在负责维护它的两位工程师。认真计算一下资源利用率；大多数规模较小的团队实际上是在为自己购买一个更差、更昂贵的 API。

## 三张发票，附有注释。

**削减 87%成本。** 一个 B2B 支持团队使用一个基于前沿模型的 14 工具 agent，收入颇丰：每月 4.6 万美元，并且随着使用量的增长而持续增长。审计发现，系统 prompt 中插入了请求 ID（缓存命中率：0%），工具加载是按请求组装的（即使 ID 已修复，前缀仍然会发生变化），而且每次调用——包括相关性检查——都基于大型模型。经过两个迭代周期，我们进行了三项更改：稳定的前缀（账单金额自然下降了一半以上），将 11 个呼叫站点静态路由到一个小型模型，并对 30%的重复问题进行结果缓存。核心模型不变，评估分数不变，每月成本降至 6100 美元。除了首席财务官之外，其他人的工作流程都没有改变。

**价值 11,000 美元的周末。** 一个没有迭代次数限制的代码迁移 agent 在周五晚上遇到了一个不稳定的测试运行程序。该工具出现了不确定的故障；这位 agent——勤奋、不知疲倦、完全无人监管——连续尝试了各种不同的测试方案，持续了 61 个小时。跟踪记录其实很精彩：一个死循环的特征（文章二）像壁纸一样不断重复，每次循环都会产生一个越来越长的测试记录（agent 成本的体现）。所有修复方案都很简单，都很枯燥，但都在周三之前全部完成：50 次迭代的上限，每个任务的预算加上检查点和停止机制，以及在每任务成本 p95 设置异常警报。预防的总成本：一天。团队把发票的截图裱了起来。

**利润率的扭转。** 一家研究报告初创公司，定价每月 29 美元，发现其多 agent 流程每份报告的成本高达 19 美元——包括协调器和六个子 agent，所有子 agent 都是前沿技术，且全部采用交互式定价，而用户通常要到第二天早上才能查看结果。重新设计后，在保持质量的同时，彻底改变了成本结构：整个流程采用批量 API（一夜之间价格降低 50%），六个子 agent 中的两个被集成到协调器中（它们是单次调用工具，但需要支付全额费用），检索和摘要功能被下放到带有 schema 验证的小型模型，并且每份报告都设定了固定预算。新的成本：2.80 美元。产品并没有变差，反而实现了盈利——而真正证明质量不变的，是评估套件，而不是用户的感觉。

## 故障模式：现场指南

团队肆无忌惮烧钱的六种方式：

1. **清除缓存的时间戳。**prompt 顶部的一行信息非常不稳定，90% 的折扣就此消失。比较两次连续请求的差异，几分钟就能找到。
2. **平均成本。** 平均值是 12 美分；p99 的恶性循环显示是 40 美元。要么看百分位数，要么瞎蒙——二选一。
3. **凭感觉做路线规划。** “这一步感觉很容易”并不代表路线规划的有效性。要用数据做路线规划：在真实交通流量下以影子模式运行小型模型，进行测量，然后再进行切换。
4. **优化 token 并减少重试次数。** 在静默重试策略导致调用量增加三倍的情况下，减少 15% 的提示时间无异于重新摆放躺椅。应该先计算每个任务的调用次数，而不是每次调用的 token 数。
5. **忘记思考标记。**推理努力被视为产出，并按产出价格计费。每次调用都采用无限制的思考预算，这构成了一种新的时间戳反模式。
6. **默认倍率 15 倍。** 生成子 agent 是因为框架本身就很容易实现。每个子 agent 都需要重新购买入场费；确保每个子 agent 都能通过努力赚取这笔费用。

## 你第一周负责成本报道

与剧集其他部分一样，结束仪式持续一周，而不是一个季度：

**第 1-2 天：查看。** 如果追踪数据中没有 token 计数和缓存统计信息，请将其提取出来。创建两个图表：有效投入价格与标价对比图，以及单任务成本百分位数图。目前暂无更改。

**第三天：稳定。** 比较连续请求的差异。消除前缀变更——时间戳、请求 ID、工具顺序改变、历史记录重写。观察有效输入价格下降。这通常是本季度最大的单项成果，而且一天之内就能完成。

**第四天：设定上限。** 为每个任务设定回合上限和 token 预算，超限时设置检查点。你的 p99 现在有了上限，睡眠质量也有所改善。

**第五天：路由。** 标记你的调用点。将明显是机械操作的调用点移到小型模型上，并放在现有 eval 的保护之后。对任何不确定的调用点进行影子测试。

**周末可选：迁移。** 找到异步任务并将其移至批处理队列。你可能已经有这样的队列，价格只要一半。

然后，在团队仪表盘上添加一个数字——完成任务的综合成本，并标明百分位区间——并在审查质量的同一会议上进行审核。现在，成本和质量已成为同一议题。这并非负担，而是成熟度的里程碑。这意味着你们的产品正在顺利运行。
