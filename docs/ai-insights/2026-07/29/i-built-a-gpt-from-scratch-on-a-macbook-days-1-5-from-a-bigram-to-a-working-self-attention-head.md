所以，每当一个问题萦绕不去，我都会做同样的事：开一个副项目。我把它叫做 `handmade-gpt`，规则很简单——在我的 M4 Pro Mac（PyTorch 跑 MPS 后端）上，一层一层手敲出一个 GPT 风格的语言模型，从最笨的模型开始，一路挣到真正的自注意力。不用 `nn.MultiheadAttention`，也不用 `nn.Transformer`——**想搞懂齿轮，就得自己把齿轮切出来。**

本文是第一个检查点：第 1 天到第 5 天，外加一段我忍不住绕的路。你看到的每一个数字都来自我机器上的实际运行，而不是教科书——因为整件事的意义就在于亲眼看着它发生。

### 首先，我们来谈谈什么是注意力，以及为什么我们应该关注它。

先从我们都实际在用的功能说起：自动补全。手机键盘、Copilot、ChatGPT——底层干的事完全一样：给定目前为止的文本，预测接下来是什么。这些工具做的全部，就是把这一个动作重复成千上万次。

仔细一想，这个动作有个显而易见的问题：***要想准确预测下一个词，不能只看最后一个词***。拿这句话来说：*“I grew up in France, so I speak fluent \_\_\_.”*（我在法国长大，所以我说一口流利的 \_\_\_。）答案是“*French*”，但给出线索的那个词（“France”）在八个词之前。只记得最近一个词的模型在这里毫无胜算，它需要某种方式回溯，把真正重要的词拉进来，无论它们隔了多远。

这种回溯正是**注意力机制**做的事。用一句平实的话说：***注意力让序列中的每个词都能看到之前的每个词，并自行判断哪些与接下来的内容相关***——不是平等地看整段历史，只看重要的那部分，并按重要程度*加权*。这就是它的全部工作。本文后面所有技术细节，都只是为了在 GPU 上高效地做成这件事的机械装置。

那么，除了背下一个定义之外，我们为什么该关心它？**因为这一个机制，就是我们每天依赖的所有模型内部的引擎。** **Transformer**——GPT、Claude、Copilot、Gemini 背后的架构——本质上就是注意力一层层叠起来。理解它，就是把这些工具当魔法，和真正知道它们为何有上下文限制、为何有时会“忘掉”长对话的开头、究竟能做什么不能做什么之间的差别。对我来说，这个理由已经足够让我停止盲用，转而动手构建。

### 说实话——我们大多数人都把“注意力”当黑盒，其实任何 LLM 都一样！！！

我们天天在用，却几乎没人能解释它*为什么*被设计成这样。

1. 为什么得分要按 `1/sqrt(head_size)` 缩放？
2. 为什么需要 Query、Key、Value 三个独立矩阵，而不是直接复用 token 自己的嵌入？
3. 为什么 Transformer 赢过了在它之前的 RNN？

我是真的不知道。我脑子里只有 LinkedIn 信息图那个版本——“**token 看其他 token，然后决定哪些相关**”——这话没错，但你一动手写代码就会发现它完全没用。

真正搭出来之后，让我意外的是：**自注意力并不是什么深奥的新数学。**它只是对一个平均运算做了个刻意的小升级，而那个平均运算你五分钟就能写完。而且几乎每一个设计选择的存在，都只出于两个原因之一：要么解决一个具体的数值问题，要么让 GPU 的日子好过一点。读完本文，你将能按我走过的顺序，从零推导出一个自注意力头，并用真实数字解释每个部件为什么在那里。

这不是面试准备。只是我陪着自己的好奇心坐了一会儿，试图和薛定谔的猫交流。

### 自注意力是跑在每个 token 内部的搜索引擎

想象一下：句子中的每个词都是一台微型搜索引擎。当“loan”这个词试图弄清楚自己在上下文里的含义时，它不只看自己，还会向前面的每一个词发出查询：*“**这里谁跟我相关？**”*

前面的每个词——“the”“bank”“approved”“my”——都像文档标题一样，提交过一条索引条目。“Bank”把自己登记在 *finance、money、building* 这类词下面。搜索引擎把“loan”的查询与每个词的索引条目比对（匹配步骤），判定“bank”以巨大优势胜出，然后取回来的不是标题，而是“bank”这份文档的实际*内容*：也就是“bank”被认定相关之后，真正贡献出来的东西。

这就是整个机制。三个角色，直接对应到技术术语：

```
| Search Engine              | Transformer Self-Attention                          |
| -------------------------- | --------------------------------------------------- |
| Search query               | **Query (Q)** — what a token is looking for         |
| Document index             | **Key (K)** — what a token exposes for matching     |
| Document content           | **Value (V)** — the information a token provides    |
| Relevance score            | **Q · K** similarity score (a dot product)                         |
| Search only past documents | **Causal Mask** — prevents looking at future tokens |
```

### 它是什么？它为什么存在？

语言模型的全部工作就是：给定目前为止的一段文本，预测下一个字符。最简单的做法是*只看当前字符*，猜它后面通常跟什么。这就是**二元语法模型**，也是我特意选的起点。

自注意力之所以存在，是因为这还不够好。真实语言有长程依赖。“The river bank was flooded”（河岸被淹了）和“The bank approved my loan”（银行批准了我的贷款）用的是同一个词，含义却截然不同，光盯着“bank”本身根本分不出来。你需要模型往*回*看——看它周围真实出现的词——并判断哪些重要。**自注意力就是让每个位置都能回看之前的每个位置，并精准取走它所需信息的那个机制。**

想象一个学生在答题。二元语法模型是只记得刚听到的最后一个词的学生。自注意力则是同一个学生被允许翻遍整本笔记，按每句话与当前问题的相关程度给它们加权。

在我看来，整个 AI/LLM 训练要做的，就是帮这个学生把泛化能力越推越远。

### 它的运作原理，以及悄然发生的错误

从机制上讲，一个自注意力头会构建出一个 `(T, T)` 矩阵——叫它 `wei`——其中 `wei[t, s]` 回答的是*“位置* `*t*` *应该对位置* `*s*` *关注多少？”*。这个矩阵来自每个 token 向量的三个学习到的投影：`Query = x @ Wq`、`Key = x @ Wk`、`Value = x @ Wv`。得分是 `wei[t, s] = Query[t] · Key[s]`。得分会被掩码，因此位置 `t` 永远看不到未来位置 `s > t`（否则模型就靠偷看答案作弊），softmax 把每一行变成真正的概率分布，最后 `wei @ Value` 产生输出——所有可见位置的 Value 按相关性加权混合而成。

我差点犯的错误——我敢打赌大多数人第一次都会犯——是以为可以跳过这三个投影，全程直接用原始 token 向量。它*确实能跑*，但悄悄破坏了两件事。第一，它强制相关性是**对称的**：`x[t]·x[s]` 永远等于 `x[s]·x[t]`，而真实的相关性不是这样运作的（“**loan**”关注“**bank**”，和“**bank**”在历史上关注“**loan**”并不是一回事）。第二，它把*“**我如何被找到**”*和*“**被找到之后我贡献什么**”*塌缩成同一个表示，从而限制了模型的表达能力。三个独立矩阵能让网络独立地调节每个角色。

### 注意力所面临的权衡：

真正把注意力和“又一层网络”区分开的，是它为了换取 GPU 并行性*放弃*了什么。历史上显而易见的替代方案，是一个从左到右走、边走边更新一个隐藏状态的循环模型。那是严格顺序的——位置 5 的状态必须等位置 4 算完才能算。对一块为同时跑上千次运算而生的 GPU 来说，这是灾难：算一步，等；再算下一步，再等，而芯片大部分区域都闲着。相比之下，**注意力的整个 `wei @ Value` 步骤只是一次矩阵乘法——所有位置的输出并行算出，一次成型。**

正是同一个权衡，*导致*得分要按 `1/sqrt(head_size)` 缩放，我会在第 5 天用实测数字证明这一点。眼下先给一行版：**更大的 head 仅仅因为累加的项更多，就会产生更大的原始得分；大得分让 softmax 饱和成一根尖峰；而饱和的 softmax 几乎没有梯度可供学习。缩放就是解法。** 好吧，严格说这不止一行，但我想大体还是能懂的。

### 我是如何一步步搭建它的

- **“第 1 天——数据管道：”**

在任何模型之前，你得先把文本变成数字。我用的是“tiny Shakespeare”——**1,115,394 个字符**的剧本和十四行诗——并且按*字符*级而不是词级做 tokenize，专门为了让词表足够小（**65 个不重复字符**），好让我能用肉眼盯住模型里的每一个数字。

```
chars      = sorted(set(text))
vocab_size = len(chars)                              
stoi       = {ch: i for i, ch in enumerate(chars)}   
itos       = {i: ch for i, ch in enumerate(chars)}   
encode = lambda s: [stoi[c] for c in s]
decode = lambda l: ''.join([itos[i] for i in l])
```

这就在字符和整数之间建立了确定性映射。紧随其后的 90/10 训练/验证划分比看上去更重要——说实话，那个 `val_data` 张量又闲置了整整两天，我才真正去读它。这后来变成了一个真正的 bug，详见第 3 天。

- **“为什么要从二元语法模型开始？”**

**二元语法模型是正确的起点，因为它是在加入任何智能之前、能证明整条流程跑得通的最小东西。** 它就是一个 `nn.Embedding(65, 65)`——一张 65×65 的查找表，**4,225 个数字，别的什么都没有。** 用一个 token 去索引它*就是*前向传播：第 `i` 行装着 65 个原始得分（“logits”），表示字符 `i` 后面通常跟什么。

```python
class BigramLanguageModel(nn.Module):    def __init__(self, vocab_size):
        super().__init__()
        
        self.token_embedding_table = nn.Embedding(vocab_size, vocab_size)    def forward(self, idx, targets=None):
        logits = self.token_embedding_table(idx)   
        loss = None
        if targets is not None:
            B, T, C = logits.shape
            
            loss = F.cross_entropy(logits.view(B * T, C), targets.view(B * T))
        return logits, loss
```

由于这是第一段真正的代码，先补两个基础概念。**张量（tensor）本质上就是一个 n 维数字数组——一维列表、二维矩阵等等——PyTorch 就在它上面做数学运算**。形状 `(B, T, C)` 是本文中反复出现的约定：***Batch（一次处理多少个序列）***、***Time（序列中的位置）***、***Channels（每个位置上的那个数字向量）***。而 `nn.Embedding` 只是一张查找表，只不过它的行是*可学习的*——反向传播每个训练步都会推动它们，这与永远不变的普通 Python dict 不同。

这里没有隐藏层，也没有非线性。`view(B*T, C)` 重塑之所以存在，仅仅是因为 `F.cross_entropy` 需要 `(N, classes)` 对应 `(N,)` 标签，而我们手上是一批序列——把 batch 和 time 展平成一维是标准做法。

从最笨的地方开始才是关键所在。它证明了整个循环——数据 → 模型 → 损失 → 反向传播 → 生成——在叠加任何真正的智能*之前*就能跑通。用 AdamW（`lr=1e-3`）训练 10,000 步，损失从随机基线 **≈4.17** 降到 **≈2.6**。这个 4.17 不是随手取的：它是 `-ln(1/65)`——恰好等于在 65 个选项里均匀猜测时的意外度（surprise）。

改进确实存在，但上限被卡得很死。看模型生成的文本，你会得到一堆英文形状的乱码：字母频率正确，偶尔蹦出一个真实的双字母组合，一个连贯单词都没有。**这个天花板*就是*那一课——这个模型除了紧挨着的前一个字符之外没有任何记忆。** *想做得更好，它必须学会回看。这就是这个项目剩下的全部内容。*

- **“第 3 天——为什么训练损失的数字在骗你”**

**单个训练批次的损失是不可靠的信号，因为它是一个方差极大的小样本——同一个未训练的模型，单批次给我 4.9046，200 批平均是 4.6666。** 相同的模型，相同的时刻，不同的数字。这个差距就是这一步存在的全部理由，而大多数教程会跳过它。

```python
@torch.no_grad()                       # measurement, not training — no backward graph
def estimate_loss():
    out = {}
    model.eval()
    for split in ['train', 'val']:     # finally reads val_data for the first time
        losses = torch.zeros(eval_iters)
        for k in range(eval_iters):    # eval_iters = 200
            X, Y = get_batch(split)
            _, loss = model(X, Y)
            losses[k] = loss.item()
        out[split] = losses.mean()
    model.train()
    return out
```

`@torch.no_grad()` 会为整个函数关掉 autograd——这是测量，所以里面任何地方都没有 `.backward()`，在这里建反向图只会浪费内存。遍历 `['train', 'val']` 的循环，才终于*用上*了验证集划分——它从第 1 天就存在，但直到现在都没人读过它。`model.eval()`/`model.train()` 对这张小表来说是空操作（还没有 dropout，也没有 LayerNorm），但这个习惯很重要：等那些层出现之后忘掉一次，你之后信任的每一个评估数字都会被悄悄污染。

*为什么只在报告时求平均，而不是干脆到处都用更大的批次？* 因为更大的批次不仅会改变你读取到的梯度值，还会改变每一步计算梯度所依据的基准。只在报告时求平均、训练批次保持不动，就把“我的数字可不可信”和“我的模型怎么训练”这两件事隔离开了。最终的干净读数：**train 2.5453，val 2.5313，差距 +0.0140**——没有过拟合，正如你对一张 4,225 参数的表所预期的那样。

- “**第 4 天——过去的加权平均这个技巧**”

架构的真正起点就在这里。目标是：让位置 `t` 看到它前面的*每一个*位置——而不只是 `t-1`——同时仍然输出一个固定大小的向量，这样不管走到序列多深处，都能套进同一个模型形状。

### 为什么不直接使用循环神经网络（RNN）呢？

**循环式的运行摘要是感觉最自然的选择，在这里却是错的，因为它严格顺序——步骤 `t` 必须等步骤 `t-1` 结束才能开始，白白浪费了一块为同时跑上千次运算而生的 GPU。** 作为一个搞数据结构与算法（DSA）的人，我的第一反应是运行累加器——正是 Kadane 算法的形状，`dp[i] = max(arr[i], dp[i-1] + arr[i])`，每一步只需要上一步的答案。这个直觉*就是*历史上真实存在过的替代方案：它是 RNN，`hidden[t] = f(hidden[t-1], x[t])`。一样优雅，在并行硬件上也一样致命。

于是我换了个路子，验证了四种计算同一个因果运行平均的方法，并检查它们完全一致：

```

tril  = torch.tril(torch.ones(T, T))
wei   = tril / tril.sum(1, keepdim=True)   
xbow3 = wei @ x
print(torch.allclose(xbow1, xbow3, atol=1e-6))  
```

双重 `for` 循环（正确，但慢）、`torch.cumsum` 的运行均值（向量化、`O(T)`，压根不需要 `(T, T)` 矩阵）、这个三角矩阵 matmul，以及同一个 matmul 的“对被掩码的零做 softmax”版本——四种都给出了完全相同的数字。

**为什么要留着 matmul**——既然 `cumsum` 对这个具体问题确实更高效？因为 `cumsum` 只给你正确答案，*别的什么都不给*。matmul 版本把 `wei` 显式暴露成一个对象：一个真实的 `(T, T)` 矩阵，表示*“位置* `*t*` *应该对位置* `*s*` *依赖多少”*。`cumsum` 永远产不出这个对象——也就没有东西可供以后升级。对*这个*窄问题来说，matmul 是更差的答案，却是唯一能把下一个问题接上的答案。这就是它出现在这里的全部原因。

- **“第 5 天——把这个技巧变成真正的自注意力：”**

第 4 天的 `wei` 是硬编码的均匀权重——每个可见的历史位置权重相同。第 5 天的全部内容，就是用真实的、*学到的*、依赖内容的得分把它换掉，途径是 Query/Key/Value：

```
key   = nn.Linear(n_embd, head_size, bias=False)
query = nn.Linear(n_embd, head_size, bias=False)
value = nn.Linear(n_embd, head_size, bias=False)k = key(x)
q = query(x)
wei = q @ k.transpose(-2, -1) * head_size ** -0.5    
wei = wei.masked_fill(tril == 0, float('-inf'))       
wei = F.softmax(wei, dim=-1)v   = value(x)
out = wei @ v   
```

这里再快速交代两个部件：`nn.Linear(in, out)` 只是一个可学习的矩阵，把大小为 `in` 的向量映射成大小为 `out` 的向量——这里它把每个 token 的向量投影到 Query、Key、Value 空间——而 `F.softmax` 接收一行原始得分，把它变成一组求和为 1 的正数，也就是“*该给每个位置分配多少注意力*”的概率分布。

正是这三个投影，打破了原始点积会强加的虚假对称。`masked_fill(tril == 0, float('-inf'))` 在 softmax *之前*把所有未来位置送到负无穷，于是 softmax 把它们变成恰好为零的概率——模型在字面意义上无法关注未来。而是 `wei @ v` 而不是 `wei @ x`，这个细节最容易把人绊倒：***决定*相关性的东西（Key），不必是被*往前传递*的东西（Value）。**

- **“为什么要把注意力得分除以 √head\_size？”**

**注意力得分要除以** `**sqrt(head_size)**`**，是为了阻止 softmax 饱和——不缩放时，我这次运行的得分方差是 2.08；除以** `**sqrt(16)**` **之后降到 0.13，正好是** `**2.08 / 16**`**，与** `**Var(c·X) = c²·Var(X)**` **吻合。** 这不是教科书上的说法，而是我打印出来的测量结果。然后我把同一行数据分别用两种方式做了 softmax。不缩放时，一个位置抓走了大约 **49%** 的概率质量，其余位置远低于它。缩放之后，同一行摊开成各位置大约 **0.09–0.20**。这就是饱和问题在真实数字里的样子——你还能看着第 4 天那种均匀的一行 `[0.25, 0.25, 0.25, 0.25]`，在得分被学出来之后变成依赖内容的 `[0.21, 0.15, 0.52, 0.12]`。饱和的 softmax 除了峰值之外处处梯度接近于零，所以训练早期，模型根本没法学会去关注其他相关位置。

### 我忍不住绕的那段路——一个注意力头 vs. 一个二元语法模型，跑真实的莎士比亚

第 4 天和第 5 天是在玩具 `torch.randn` 张量上验证机制——数学正确，但和任何真实文本都没关系。我不打算一直等到路线图走到“组装完整 block”那天，才去弄清楚这一切*到底有没有用*。于是我脱了稿，把一个真实的 head 接进一个可训练模型——token 嵌入、位置嵌入、一个 `Head`、一个最终的线性 `lm_head`——用真实的 tiny Shakespeare 训练，同时并排训练一个全新的二元语法模型，两边的 `block_size=8`、`batch_size=4` *完全一致*。

下面是诚实的结果。**最终验证损失几乎没动：注意力 2.4552，二元语法 2.5402。** 如果只看这个数字，我大概会耸耸肩。真正的故事在于各自*多快*走到那里：**注意力在约 2000–3000 步就接近了它的最终损失，二元语法则需要 9000 步以上。** 相同的数据，相同的超参数——注意力就是显著更早地学到了有用的结构。我还检查了两边的 train/val 差距（注意力 **−0.009**，二元语法 **+0.006**），确认这场胜利来自泛化，而不是注意力模型多出来的参数（**7,553 对 4,225**）在悄悄背答案。

生成的文本呢？两边都还是乱码。这在意料之中——一个 head，没有 MLP、没有残差连接、没有 LayerNorm、也没有多头，写不出莎士比亚。重点不是连贯的文本，而是亲眼看着“模型可以回看不止一个字符”从一个玩具想法，变成一条可测量的、更快的学习曲线。

这个训练出来的模型需要一样二元语法从不需要的东西：**位置嵌入**。二元语法的预测只取决于当前 token 的身份——“'F' 后面跟什么”是同一个问题，不管这个 'F' 是第 1 个还是第 50 个字符。注意力打破了这一点，因为 `q[t]·k[s]` 只看得到*内容*——点积里没有任何东西告诉模型 `s` 是前一步还是后七步。所以每个 token 的向量变成了 `token 含义 + 位置` 的加和。这张表恰好只有 `block_size` 行，也就埋下了下一节里的第一个 bug。

### 把我绊倒的那些事

这些不是假想的“常见错误”，而是在这次构建中实实在在耗掉我时间的那些。

- **“相信单个训练批次的损失”**

我从一个批次里读出 `loss.item()`，就把它当成了真值。但 32 个样本的批次是个高方差样本——同一个未训练的模型给了我 4.9046 和 4.6666。单批次的输出看多了，你会说服自己相信一个并不存在的进步（或退步）。解法是 `estimate_loss()`：*只在报告时*对多个批次求平均，训练样本的数据保持不动。

- **“忘了验证集划分的存在”**

我在第 1 天就把数据划分好了，然后连着两天只调用 `get_batch('train')`。没有 `val_data`，就没办法发现过拟合——你看到的永远只是模型对它已经背下来的文本拟合得多好。真正管用的修法是：让损失报告函数默认遍历*两个*划分，这样用上 `val_data` 就不再是一件需要谁去记住的额外步骤。

- **“把原始向量同时当 Query、Key 和 Value 用”**

诱人的第一版是 `wei = x @ x.transpose(-2, -1)` 然后 `out = wei @ x`——同一个向量干完三份活。它能跑，但它强制相关性对称，还把“**是什么让我可被找到**”和“**被找到之后我交出什么**”塌缩到了一起。三个独立的学习投影一次解决这两个问题。

- **“跳过** `**1/sqrt(head_size)**` **缩放”**

把 `q @ k.transpose(-2, -1)` 直接喂进 softmax，看着没毛病，直到你去测方差——这里不缩放是 2.08。大得分把 softmax 推向近乎 one-hot 的输出，而饱和的 softmax 除了峰值之外几乎没有梯度，学习就此停滞。一行修法 `* head_size ** -0.5`，让方差基本保持恒定，与 head 大小无关。

- **“生成时让上下文窗口悄悄溢出”**

这就是位置嵌入埋下的那个 bug。我的二元语法 `generate()` 循环每一步都把不断变长的整个序列喂回去，这本来没问题——反正二元语法只用最后一个 token。但位置表只有 `block_size` 行，喂进更长的序列就会索引越界。修法是每次前向传播之前先裁剪：

```
idx_cond = idx[:, -self.block_size:]   
logits, _ = self(idx_cond)
```

### 放到真实规模上是什么样（好奇一瞥版）

上面这一切都跑在玩具级的 `block_size=8` 和单个 head 上。真正的生产级 LLM 跑的是*完全相同*的机制——一样的 Query/Key/Value、一样的缩放、一样的因果掩码——只是在那个规模上，上面每一个选择都会迅速变贵。搭完小版本之后，有几件事我理解得更清楚了：

- **KV 缓存。** 推理时，每来一个新 token 就从头重算完整的 `(T, T)` 注意力矩阵，意味着每一步都要为整段不断变长的上下文重算 Key 和 Value 向量——平方级，而且很残酷。真实系统会缓存已见 token 的 Key/Value 向量，只为新 token 计算 Q/K/V。这就是我那个上下文裁剪 bug 的成人版：不是简单截断，而是小心管理一份不断增长的缓存的内存，因为它同时随序列长度和 batch size 增长。
- **上下文窗口的上限，直接来自位置嵌入是一张固定大小的表**——正是咬了我一口的那个东西，只是在那个规模上，修法不再是“把输入裁掉”，而是像旋转位置嵌入（RoPE）这类更聪明的位置方案，避开硬性截断。
- **专用的注意力 kernel（FlashAttention 及其同类）** 之所以存在，一部分原因是：当初促成 `1/sqrt(head_size)` 的那个方差增长问题，会在 `fp16`/`bf16` 精度下以真正的上溢/下溢重新冒出来——所以 softmax 这一步被大幅优化，而不是老老实实写成一个朴素 matmul。

这些我一个都还没亲手实现过。但我测出来的这些玩具数字，正是在大规模下会变成真实生产事故的那些数字——从笔记本上一个 7,553 参数的模型意识到这一点，是种奇怪的满足感。

### 我的收获：

- **二元语法证明了整条流程能跑通**，但它的天花板低到不能再低：除了紧挨着的前一个字符，没有任何记忆。
- **你的训练损失比你以为的更嘈杂**——相信它之前先对很多批次求平均，也别忘了还有验证集划分。
- **循环式的运行摘要感觉很自然，但它是顺序的**，这正是它在 GPU 上输给注意力那一次并行 matmul 的原因。
- **自注意力是每个 token 内部的搜索引擎**：Query 负责问，Key 负责被匹配，Value 负责被返回——而它们是三个独立的矩阵，这是故意的。
- `**1/sqrt(head_size)**` **不是装饰**——它是 softmax 保持平滑混合、还是坍缩成一根尖峰之间的分界线（我这次运行里方差 2.08 → 0.13）。
- **诚实的胜利不在最终损失**（2.4552 对 2.5402）——而在于注意力用约 2000–3000 步就达到了那个损失，而不是 9000 步以上。
